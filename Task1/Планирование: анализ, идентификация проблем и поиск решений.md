# architecture-alexandrite

### Существующие и потенциальные проблемные места
- **Для сложных моделей ювелирных изделий слишком долго считается стоимость работы**
- **Большое количество заказов упирается в медленный механизм расчета стоимости в MES**
- **Клиенты не получают заказы месяцами при обещанных 3 неделях**
- **Жалобы на просроченные заказы от клиентов**
- **Жалобы от операторов, что долго грузится первая страница MES**
- **Недовольство клиентов онлайн магазином**
- **Ненадежная событийная интеграция (MES ↔ CRM через RabbitMQ), возможны потеря/дубликаты сообщений**
- **Ручное E2E-тестирование тормозит релизы; В CI/CD пайплайне не хватает автотестов**
- **По одному инстансу приложений; один инстанс БД на чтение/запись; Нет горизонтального масштабирования**
- **Нет сквозной трассировки/метрик для событий/очередей/статусов**
- **Сервис онлайн магазина и CRM-сервис используют одну БД, что является антипаттерном**
- **Риски команды: один DevOps, QA без зрелой авто-автоматизации, фронтендер без хорошего знания React; рост без усиления компетенций приведёт к потерям качества**

### Инициативы, которые необходимы для устранения нежелательных ситуаций
- **Добавить больше логирования в каждой системе, чтобы проще определять проблемные места**
- **Настроить мониторинг RabbitMQ, алерты**
- **Добавить кеширование**
- **Внедрить outbox/inbox-паттерны, идемпотентных потребителей**
- **Автоматизировать деплой на release-окружение при мерже в release ветку либо при проставлении тега на эту ветку**
- **Добавить OpenTelemetry трассировку сквозных запросов/событий; метрики бизнес-SLA**
- **Репликация БД(Shop DB, MES DB). В перспективе нужно выделить для CRM-сервиса отдельную БД, но пока что с этой нагрузкой будет справляться реплика**
- **Добавить алерты на превышение пороговых значений параметров мониторинга**
- **Нужен сопровожденец, чтобы взять на себя вопросы поддержки приложения с продакт-менеджера и реагирование на инциденты и внештатные ситуации**
- **Нужен лид фронтенда со знанием react**
- **Нужен SRE для подготовки инфраструктуры мониторинга и улучшения надежности приложения, а также постепенного перевода системы на Kubernetes, чтобы появилась возможность масштабировать инстансы приложения**
- **Внедрить автотесты в CI пайплайн**

### Инициативы в порядке приоритета
Целевая архитектура через полгода: 
Улучшена наблюдаемость, надежность приложения: мониторинг, логирование, трейсинг. Используются ELK-стек, Prometheus, Grafana. 
Стабилизирована событийная интеграция между компонентами системы. Проведена оптимизация быстродействия - кеширование, реплика БД на чтение.

Основные три пункта на ближайшие 3 года:
1) Нужно собрать больше данных о проблемных местах в интеграциях внутри приложения. Для этого стоит реализовать мониторинг, логирование, трейсинг.
2) Стабилизовать событийную интеграцию, чтобы не терялись заказы, так как это основная боль бизнеса при возросшей нагрузке.
Реализовать ack, nack, DLE(Q) в RabbitMQ для увеличения надежности обработки событий и ретраи на уровне сервисов;
3) Оптимизация быстродействия. Добавлено кеширование, как минимум в сервисе MES, чтобы быстрее прогружалась первая страница для операторов. 
А по результатам анализа данных мониторинга уже можно точечно добавить кеширование в другие части приложения.
А также добавлена реплики БД на чтение для Shop DB и MES DB.
