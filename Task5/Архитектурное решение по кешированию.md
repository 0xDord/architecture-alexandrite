# architecture-alexandrite

### Мотивация
Для оптимизации работы операторов с системой MES, следует добавить кеширование на MES API.
Ускорит дашборд с фильтром, оптимизирует mes api для всех клиентов.

### Предлагаемое решение
Внедряем серверное кеширование. MES API используют не только операторы(через фронт системы MES), но и внешние клиенты, нагрузка на БД повышается, можно оптимизировать. 
Если использовать клиентское кеширование на MES, то можем чаще получать устаревшие данные по заказам, гибко выбрать TTL не выйдет.
В других компонентах системы кеширование не критично.

Так как компанию завалило заказами после открытия MES API для других продавцов, то ювелирных изделий, 
значит увеличилось количество размещений заказов от них, а следовательно это операции записи.
Также популярны и операции чтения от операторов.
Предлагается использовать механизм смешанный механизм кеширования **Read-Through + Write-Through**.
При запуске сервисов делаем прогрев кеша.
В подходе Cache-Aside нужно дорабатывать код приложения и этот подход предпочтителен при высоких нагрузках при операциях чтения.
Write-Behind сложнее в реализации, чем Write-Through, так как нужно иметь буфер, очередь, ретраи, и помимо этого возможна временная рассогласованность между кэшем и БД.
Для повышенной консистентности и надежности предлагается выбрать Write-Through.

Стратегия инвалидации кеша:

| Способ инвалидации кеша             | Описание                                                                                                                                                               | Возможность использования |
|-------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------|
| Временная инвалидация               | Плюсы: простота реализации, отлично подходит для данных, которые редко меняются<br/> Минусы: устаревшие данные между инвалидациями; не подтягивает real-time изменения | не подходит               |
| Инвалидация, основанная на запросах | Вариант подходит, так как выборочно инвалидируется кеш, когда оператор берет заказ в работу, он исчезает из кеша и другие операторы не видят этот заказ на странице    | подходит                  |
| Инвалидация на основе изменений     | Вариант подходит, схож в логике работы с предыдущим вариантом                                                                                                          | подходит                  |
| Программная инвалидация             | Можно гибко управлять инвалидации, доработать код при возникновении новых условий для инвалидации                                                                      | подходит                  |
| Инвалидация по ключу                | При изменении статуса заказа, можно по ключу инвалидировать его, что весьма удобно, так как не нужно инвалидировать все данные                                         | подходит                  |

Остановимся на программной инвалидации из-за гибкости в управлении этим процессом
