# architecture-alexandrite

### Логирование

- Shop API:
  - Создание/изменение заказа: время операции, id заказа, id клиента, id сессии, параметры заказа
  - Загрузка 3D‑файла: время операции, id заказа, id клиента, метаданные файла
  - Отправка заявки на расчёт цены в RabbitMQ: время операции, id заказа, payload
  - Внешний API вызовы: время операции, id заказа, тело запроса 

- CRM API:
  - Получение события из RabbitMQ: время операции, id заказа, тип события, payload
  - Изменение статуса: время операции, id заказа, старое значение статуса, новое значение статуса
  - Отправка события в RabbitMQ (MANUFACTURING_APPROVED/CLOSED): время операции, тип события, id заказа, payload

- MES API:
  - Принятие заказа в работу оператором: время операции, id заказа, id оператора
  - Постановка задачи на расчёт цены: время операции, id заказа, id задачи, параметры заказа
  - Завершение расчёта цены: время операции, id заказа, id задачи, цена заказа

- RabbitMQ:
  - Публикации: время операции, id сообщения, payload
  - Потребление: время операции, id сообщения, payload
  - DLQ: время операции, id сообщения, payload, причина попадания в dlq

- Использование других уровней логирования:
  - DEBUG: бизнес логика и операции в сервисном слое
  - WARN: таймауты, ретраи, частичные сбои
  - ERROR: ошибки бизнес‑операций (невозможность изменить статус, запись в DLQ), необработанные исключения, превышение кол-ва ретраев
  - FATAL: недоступность сервиса - API, S3, RabbitMQ

### Мотивация

Логирование повышает наблюдаемость ключевых бизнес‑потоков (создание/расчёт/производство заказа), ускоряет поиск причин пропавших заказов и деградаций в MES сервисе, снижает время реакции на инциденты.
- Метрики, на которые влияет внедрение:
    Технические: время недоступности сервисов/инфраструктуры, процент сообщений в DLQ, количество таймаутов, доля ошибок 5xx
    Бизнес: доля просроченных заказов, среднее время до начала производства заказа, количество утраченных/дублированных заказов
- Приоритет логирования систем:
  1) MES API и очередь RabbitMQ — максимальный вклад в стабильность статусов и расчёта цены, для бизнеса это наиболее критичные части системы, в которой сейчас возникают сложности
  2) CRM API — источники и потребители статусов заказа, исправление проблем с переходом заказов по статусам, исключение ситуаций с потерей заказов 
  3) Shop API и внешний партнёрский API — контроль входящего потока, идемпотентность и SLA для партнёров

### Предлагаемое решение
- Технологический стек:
  - Структурированное логирование с помощью Logback
  - Сбор логов со всех сервисов - Logstash
  - Централизованное хранение логов и поиск по ним - ElasticSearch
  - Визуализация - Kibana

Схема с новыми компонентами логирования:
[jewerly_c4_logging.drawio](jewerly_c4_logging.drawio)

- Политика безопасности для логирования:
  - Не выводить в лог ПДн клиентов и операторов, токены,куки
  - Доступ на просмотр логов у SRE, DevOps, разработчиков и сопровождения
  - Доступ на изменение конфигураций ELK - SRE, DevOps
  - Шифрование на транспортном уровне - TLS

- Политика хранения:
  - Индексация под каждый сервис системы
  - Период хранения: 30 дней горячее хранение; 180 дней тёплое/архив; dev/release — 7 дней
  - Квоты на размер: чтобы оценить квоту на размер памяти под логи нужно знать количество клиентов на данный момент. В целом можно выделить 100 ГБ места и при надобности расширять;

### Алерты
  - Рост DLQ > X сообщений за Y минут
  - 95/99 перцентиль latency на основных эндпоинтах выше целевого SLO
  - Процент 5xx ошибок/ретраев выше порогового в Shop/CRM/MES выше X% в течение Y минут
  - Лаг потребления очереди > X секунд

- Аномалии и защита:
  - Детектор аномалий по частоте создания заказов/запросов API партнёров (подозрение на DDoS)
